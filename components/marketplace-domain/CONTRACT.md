# `marketplace:domain` — the contract

A multi-vendor marketplace: vendors list items, buyers ask about them, buy them,
get shipped to, can dispute or return, and vendors get paid out through a real
double-entry ledger. Five parts write this at the same time, against this file.
It is the only thing they share, so anything not written here is not agreed. If
it is wrong or missing something you need, write `CONTRACT-REQUEST.md` — first
line the subject, the rest why — and the other parts answer between
generations. Do not edit this file.

**Parts do not call each other's Rust code.** They interact ONLY through
`records:store` collections (this contract's shapes) and shared `fsm:workflow`
machine instances (this contract's machine names and events). A part that
needs a value from another part's collection reads that collection directly.

## Roles

`vendor`, `buyer`, `admin`. Anyone may register as any of the three; the
default for an unrecognised or absent role is `buyer`. A listing's `vendor`
field is whoever created it — there is no separate vendor-profile collection.

## The stored documents

### `listings` (owned by part 1, read by parts 1, 2, 3, 5)

```json
{
  "vendor": "usr_...",
  "title": "Mechanical keyboard",
  "description": "Hot-swappable, brown switches",
  "price": 4500,
  "stock": 12,
  "category": "electronics",
  "category_confidence": 850,
  "status": "active"
}
```

- `price` is an integer, minor units (cents).
- `category` is auto-set on creation by Jev (see below) from a FIXED taxonomy:
  `"electronics"`, `"clothing"`, `"home"`, `"books"`, `"toys"`, `"other"`. The
  vendor who owns the listing may change it afterward with a plain field
  update — Jev drafts, the vendor may override, exactly once either way is
  final (no re-running Jev after a manual edit).
- `category_confidence` is Jev's own reported confidence, milli-units (0-1000),
  stored for anyone reading the listing to see how sure the auto-label was.
- `status` is `"active"` or `"delisted"` (vendor or admin may delist; a
  delisted listing cannot be ordered or messaged about, but past orders
  referencing it are unaffected).
- Indexed fields, passed to `records::create`: `vendor`, `status`.

### `orders` (owned by part 1, transitioned by parts 1 and 2, read by 1/2/3/4)

```json
{
  "buyer": "usr_...",
  "items": [{"listing_id": "...", "quantity": 2, "unit_price": 4500}],
  "total": 9000
}
```

- `unit_price` is copied from the listing AT ORDER TIME (a later price change
  must not change what an existing order owes).
- `total` is the sum of `quantity * unit_price` across `items`, computed by
  part 1 when the order is placed.
- Indexed fields: `buyer`.
- The order's own lifecycle state is NOT a field on this document — it lives
  entirely in the `order` fsm machine (below), instance id = the order's
  record id. `GET` routes that return an order must merge in
  `"status": <fsm state>` by calling `fsm:workflow/engine::get-status("order",
  order_id)`.

### `payments` (owned by part 2)

```json
{"order_id": "...", "refunded_amount": 0}
```

- One payment per order, instance id of the `payment` machine = the ORDER's id
  (not a separate payment id — there is exactly one payment per order in this
  contract).
- `refunded_amount` is a plain integer field on this document (NOT an fsm
  state) — a partial refund updates this number and still fires the same
  `refund` transition on the `payment` machine as a full refund does. A full
  refund is one where `refunded_amount == ` the order's `total`.
- Indexed fields: `order_id`.

### `shipments` (owned by part 2)

```json
{"order_id": "...", "carrier": "...", "tracking": "..."}
```

- Instance id of the `shipment` machine = this record's own id (NOT the order
  id — a re-shipped order could in principle get a second shipment record,
  though nothing in this contract exercises that).
- Indexed fields: `order_id`.

### `returns` (owned by part 2)

```json
{"order_id": "...", "buyer": "...", "reason": "..."}
```

- May only be created once the `order` machine's instance for `order_id` is in
  state `delivered`.
- Instance id of the `return` machine = this record's own id.
- Indexed fields: `order_id`.

### `disputes` (owned by part 3)

```json
{
  "order_id": "...",
  "buyer": "...",
  "reason": "Item never arrived",
  "resolution": "",
  "jev_recommendation": "",
  "jev_confidence": 0
}
```

- May be opened at any point where the `order` machine's instance for
  `order_id` is NOT YET in state `delivered` (once delivered, the buyer's only
  path is a return, above — disputes and returns are mutually exclusive by
  when they may be opened, not by a shared field).
- `resolution` is `""` until an admin resolves it, then one of `"refund"`,
  `"deny"`, `"partial"`.
- `jev_recommendation` / `jev_confidence` are filled in immediately on
  creation by the Jev advisory call (below) and are informational ONLY — the
  route that resolves a dispute takes the admin's own `resolution` from the
  request body and never reads these fields to decide anything. Same rule
  `graph-selector::land` already follows elsewhere in this repo: a model may
  advise, never decide.
- Instance id of the `dispute` machine = this record's own id.
- Indexed fields: `order_id`.

### `ledger_entries` (owned by part 4)

```json
{"memo": "order 01ABC sale", "lines": [{"account":"platform:cash","amount":9000,"side":"debit"},{"account":"vendor:usr_...","amount":8100,"side":"credit"},{"account":"platform:fees","amount":900,"side":"credit"}]}
```

- Every entry MUST be validated with `ledger:doubleentry/ledger::validate`
  before it is stored — an entry that fails validation is a bug in the caller,
  not a 400 to any HTTP client, since nothing external supplies these lines.
- The platform fee is a FLAT 10% of an order's total, taken on sale.
- Account naming, fixed: `vendor:<subject>` (one account per vendor),
  `platform:cash`, `platform:fees`. Nothing else posts to these three
  prefixes.
- A sale posts: debit `platform:cash` (the total), credit `vendor:<subject>`
  (total minus 10% fee), credit `platform:fees` (the fee) — three lines, one
  entry, debits == credits.
- A refund (full or partial, amount = the refunded amount) posts: debit
  `vendor:<subject>` (the refunded amount), credit `platform:cash` (the same
  amount) — two lines. The vendor eats the refund; the fee is not reversed
  (already earned for processing the sale).
- Indexed fields: none required (small enough to `list_records` in full for
  aggregation — see routes below).

### `inquiries` + `messages` (owned by part 5)

```json
// inquiries
{"listing_id": "...", "buyer": "...", "vendor": "..."}
// messages
{"inquiry_id": "...", "sender": "...", "body": "..."}
```

- `inquiries.vendor` is copied from the listing at inquiry-creation time (so a
  listing changing hands, if that were ever possible, would not retarget past
  inquiries — nothing in this contract lets a listing change vendor, this is
  just the same "copy at creation" discipline `orders.items[].unit_price`
  already follows).
- Indexed fields: `inquiries` on `buyer` and `vendor`; `messages` on
  `inquiry_id`.

## The five machines (all via `fsm:workflow/engine`, defined once at startup by
## whichever part's code path runs first — `define` on an already-defined name
## just replaces it with the same definition, which is harmless)

```
order:     placed --pay--> paid --ship--> shipped --deliver--> delivered
           placed --cancel--> cancelled
           paid --cancel--> cancelled
           terminal: delivered, cancelled

payment:   authorized --capture--> captured --refund--> refunded
           terminal: refunded

shipment:  label_created --dispatch--> in_transit --deliver--> delivered
           terminal: delivered

return:    requested --approve--> approved
           requested --reject--> rejected
           terminal: approved, rejected

dispute:   open --resolve--> resolved
           terminal: resolved
```

Firing `shipment`'s `deliver` event (part 2) MUST also fire `order`'s `deliver`
event on the same order id, in the same request — a shipment cannot be
delivered while its order is not. If the order's `deliver` fails (wrong
state), the whole request fails with the order machine's error; the shipment
transition must not be left half-applied. `fsm:workflow` has no cross-machine
transaction, so fire the shipment's own transition SECOND, after confirming
the order's `deliver` succeeds — a failed shipment-delivery attempt must not
firing on an order not yet in `shipped`.

## Jev usage (`jev:decision/decision`, imported once, used two ways)

**Listing auto-labeling** (part 1, on `POST /api/listings`): a `choose`
request — `state` is the listing's title + description concatenated,
`instructions` asks which category best fits, `options` is the six-item fixed
taxonomy above. The `selected` option becomes `category`; `confidence`
(0.0-1.0 float from Jev, multiplied by 1000 and rounded) becomes
`category_confidence`. If the Jev call fails for any reason
(`decision-error`), the listing is still created — `category` falls back to
`"other"`, `category_confidence` to `0`. A labeling failure must never refuse
the listing itself.

**Dispute advisory** (part 3, on `POST /api/disputes`): a `gate` request —
`state` is the dispute's `reason` plus the order's `total`, `true-hint` is
"the buyer's claim looks legitimate and a refund is warranted", `false-hint`
is "the claim looks weak or abusive". The `probability` becomes
`jev_confidence` (same 0-1000 scale) and a `probability >= 500` sets
`jev_recommendation` to `"refund"`, otherwise `"deny"`. Same failure rule as
labeling: a Jev failure must not refuse dispute CREATION — leave
`jev_recommendation` empty and `jev_confidence` at 0, and let an admin resolve
it with no advisory at all.

## Routes

### Part 1 — `catalog.rs`: listings and order placement

- `POST /api/listings` `{"title","description","price","stock"}` (vendor) →
  `201` with the document + id, `category`/`category_confidence` filled in as
  above. `400` if `title` empty, `price` not a positive integer, or `stock`
  negative.
- `PATCH /api/listings/{id}/category` `{"category"}` (the listing's own
  vendor, or admin) → `200`, refuses (`400`) a category outside the fixed
  taxonomy. Sets `category_confidence` to `1000` (a human is now certain).
- `GET /api/listings` (any authenticated) → `{"listings":[...]}`, only
  `status == "active"` ones, newest first. `?category=` filters.
- `GET /api/listings/{id}` (any authenticated) → the document, `404` if
  missing OR delisted (a delisted listing 404s for everyone but its own
  vendor/admin, who still see it).
- `POST /api/listings/{id}/delist` (the listing's own vendor, or admin) →
  `200`.
- `POST /api/orders` `{"items":[{"listing_id","quantity"}]}` (buyer) → `201`
  with the order + id. Every listed item must exist, be `active`, and have
  `stock >= quantity` — checked for ALL items before any stock is decremented
  (an oversell on item 2 of 3 must leave item 1 untouched), `409` naming the
  first insufficient listing if not. On success: decrements every listing's
  stock, creates the order document, creates an `order` fsm instance in state
  `placed`. `400` if `items` is empty.
- `GET /api/orders` (buyer sees own; admin sees all) → each with `status`
  merged in from the fsm.
- `GET /api/orders/{id}` (the order's own buyer, or admin, or the vendor of
  ANY item in it) → `403` otherwise, `404` if missing.

### Part 2 — `fulfillment.rs`: payments, shipments, returns

- `POST /api/orders/{id}/pay` (the order's own buyer) → creates the `payments`
  document (`refunded_amount: 0`), creates a `payment` fsm instance in
  `authorized`, immediately fires `capture` (this contract has no separate
  authorize-then-capture HTTP step), fires the `order` machine's `pay` event,
  and posts the SALE ledger entry described in `ledger_entries` above (debit
  `platform:cash` the order's `total`, credit `vendor:<subject>` total minus
  10%, credit `platform:fees` the 10%) — payment capture is the point money
  actually changes hands, which is why the ledger entry lives here and not on
  `POST /api/orders`. `409 {"error":"illegal_transition"}` if the order isn't
  `placed`.
- `POST /api/orders/{id}/ship` `{"carrier","tracking"}` (admin, or the vendor
  of any item in the order) → creates the `shipments` document, a `shipment`
  fsm instance in `label_created`, immediately fires `dispatch` (moves it to
  `in_transit`), fires the `order` machine's `ship` event. `409` if the order
  isn't `paid`.
- `POST /api/shipments/{id}/deliver` (admin) → fires the `shipment` machine's
  `deliver`, THEN the `order` machine's `deliver` (via the shipment's own
  `order_id` field) — see the cross-machine rule above. `409` naming whichever
  machine refused.
- `POST /api/orders/{id}/refund` `{"amount"}` (admin) → refuses (`400`) if
  `amount` plus the payment's existing `refunded_amount` would exceed the
  order's `total`. Updates `refunded_amount`, fires the `payment` machine's
  `refund` event (moves to `refunded` regardless of partial vs full — the
  machine only tracks that a refund happened, not how much). Posts the ledger
  entry described above (part 4's collection, written directly — parts share
  storage, not code).
- `POST /api/orders/{id}/returns` `{"reason"}` (the order's own buyer) →
  `409` unless the `order` machine's instance is in `delivered`. Creates the
  `returns` document + a `return` fsm instance in `requested`.
- `POST /api/returns/{id}/approve` and `POST /api/returns/{id}/reject`
  (admin) → fires the matching event.

### Part 3 — `trust.rs`: disputes, fraud scoring, vendor reputation

- `POST /api/orders/{id}/disputes` `{"reason"}` (the order's own buyer) →
  `409` if the `order` machine's instance is already `delivered`. Creates the
  `disputes` document, a `dispute` fsm instance in `open`, runs the Jev
  advisory call (above) and fills in the two `jev_*` fields (or leaves them
  empty on failure — never refuses the dispute).
- `GET /api/disputes` (admin sees all; a buyer sees their own) → each with
  `status` merged in from the fsm.
- `POST /api/disputes/{id}/resolve` `{"resolution"}` (admin) → `resolution`
  must be one of `"refund"`, `"deny"`, `"partial"` (`400` otherwise), fires the
  `dispute` machine's `resolve` event, stores `resolution` on the document.
  Does NOT itself move money — resolving to `"refund"`/`"partial"` is a
  decision an admin then separately actions via `POST /api/orders/{id}/refund`
  (part 2's route); this route only records the verdict.
- `GET /api/vendors/{subject}/reputation` (any authenticated) →
  `{"vendor":"...","dispute_rate":<float 0-1>,"order_count":<n>,"fraud_flags":<n>}`.
  `dispute_rate` = (count of disputes on orders containing this vendor's
  listings) / (count of orders containing this vendor's listings), `0` if the
  vendor has no orders yet, not a division-by-zero error.
- **Fraud scoring**, computed inline on `POST /api/orders` by part 1 is NOT
  how this contract splits it — part 1 calls nothing from part 3, per the "no
  cross-part Rust calls" rule. Instead: fraud scoring happens the same place
  disputes do, but retroactively — `GET /api/vendors/{subject}/reputation`'s
  `fraud_flags` counts orders where `order.total > 10000` (100 dollars) AND
  the vendor's `order_count` (orders fulfilled before this one, by `created`
  order) was `0` at the time — i.e., a large first-ever order from a vendor,
  read directly from `orders`/`listings`, no shared mutable score field
  needed anywhere.

### Part 4 — `ledger.rs`: the payout ledger

- `GET /api/vendors/{subject}/balance` (the vendor themself, or admin) →
  `{"vendor":"...","balance":<integer>}`. Loads every `ledger_entries`
  document via `records::list_records`, converts each to a `ledger:
  doubleentry/ledger` `entry`, calls `trial-balance`, and reports the `net`
  for account `vendor:<subject>` (0 if that account has no lines at all —
  `trial-balance` omits accounts with no postings, so a missing entry in the
  result means zero, not an error).
- `GET /api/ledger/platform` (admin only) → the same trial balance's
  `platform:cash` and `platform:fees` accounts,
  `{"cash":<net>,"fees":<net>}`.
- `POST /api/vendors/{subject}/payout` (admin) → posts a ledger entry that
  debits `vendor:<subject>` for its full current balance and credits
  `platform:cash` for the same amount (zeroing the vendor's balance — a real
  payout is out of scope, this is the bookkeeping event that would trigger
  one). `400 {"error":"nothing_owed"}` if the balance is `0` or negative.

### Part 5 — `messaging.rs`: inquiries and messages

- `POST /api/listings/{id}/inquiries` `{"body"}` (buyer) → creates an
  `inquiries` document (`vendor` copied from the listing) and its first
  `messages` document (`sender` = the buyer). `404` if the listing doesn't
  exist or is delisted.
- `GET /api/inquiries` (buyer sees ones where they are `buyer`; vendor sees
  ones where they are `vendor`; admin sees all) → `{"inquiries":[...]}`.
- `GET /api/inquiries/{id}/messages` (either party to the inquiry, or admin)
  → `403` for anyone else, `{"messages":[...]}` oldest first.
- `POST /api/inquiries/{id}/messages` `{"body"}` (either party to the
  inquiry) → `403` for anyone else, `201` with the new message.

## What you must not write yourself

Every part's world already contains the hard pieces, as components, bound at
compose time. What is imported is implemented, tested and composed for you —
call it, do not re-implement it. Each gate reads the compiled component's
imports, so writing your own passes the behavior and fails the gate.

- **Every lifecycle** is `fsm:workflow/engine` — `define` each of the five
  machines once (an idempotent `define` call, same discipline
  `guest_owner_or_admin_policy!` already uses elsewhere in this repo for
  idempotent setup), then `create-instance`/`fire`/`get-status` per instance.
  A hand-rolled `if status == "paid"` anywhere is the one way to fail a gate
  while answering requests that look correct in isolation.
- **The ledger invariant** is `ledger:doubleentry/ledger` — `validate` before
  every store, `trial-balance` for every balance query. A hand-rolled sum is
  the second way to fail a gate while looking correct in isolation, because
  two parts computing "the same" balance by hand can silently disagree on
  rounding or which entries to include.
- **Both Jev calls** are `jev:decision/decision` — `choose` for labeling,
  `gate` for the dispute advisory. Never treated as more than advisory,
  matching `graph-selector::land`'s own rule elsewhere in this repo: no model
  output ever appears on the right-hand side of an `if` that decides money or
  access; it only annotates a record a human later acts on.
